### One plan, one reserved execution: durable pre-GET consumption

A source plan SHA is usable by exactly one run and only runAttempt`1`. Dispatch initially creates a **held, source-free run**; no source job starts from dispatch inputs alone. Root obtains its actual run ID, verifies the exact workflow/main/source commit/preset/planSHA and attempt1 through authenticated GitHub metadata, then reserves that identity once. The claim is outside the plan hash, avoiding a future-run circular hash while binding the already reviewed plan. The held consume job polls only the deterministic claim ref derived from its reviewed planSHA; it never needs the future claim SHA as a pre-dispatch input. Root records the exact created commit/JSON SHA in its expected transport record; after create-only protected reservation the running jobs authenticate that same frozen ref and its complete execution binding.

Minimum correct durable mechanism is an atomic GitHub `POST /git/refs` creation of `refs/tags/fcf-inventory-claim/<planSha256>` pointing to a claim-only commit. Claim JSON fields are exactly `schemaVersion:1,kind:'fcf-missing-inventory-execution-claim',repository,workflow,planSha256,sourceCommit,runId,runAttempt:'1',preset,maximumSourceGETs:477,claimedUTC`. Root prepares the blob/tree/commit with GitHub's Git data API, parented on the reviewed source commit, without altering main or the user's checkout. Root reviews/pins the exact claim commit and JSON SHA; the atomic ref creation is the consumption linearization point. An existing ref, including one for a cancelled/failed/indeterminate run, rejects reservation rather than updating it. Never PATCH/force/delete/recreate the claim or move it to another run. Concurrent attempts to reserve the same name have one creator; every loser fails closed before source. The claim is consumed even if execution later makes zero GETs.

Because a Git ref alone is mutable, root must first install/verify a matching tag ruleset forbidding update and deletion of `fcf-inventory-claim/*`, with no bypass for the claim-creation identity. Creation remains permitted; mutation/deletion does not. Capture must authenticate the actual ruleset and exact ref/claim commit/JSON on every child preflight; missing protection, inaccessible/incomplete metadata, moved/missing ref or any identity mismatch holds. Root's one-time reservation uses GitHub contents:write only through its authenticated control-plane identity; capture jobs have only contents:read/actions:read and no mutation credential. If this durable create-only primitive/protection cannot be supplied, there is no correct source-enabled fallback; keep the run held. Workflow concurrency or listing artifacts followed by uploading one is not an atomic consumption mechanism.

A source-free `missing-inventory-consume` job reads and verifies that exact root claim, actual run identity, attempt1, approved plan and seed, then uploads one immutable `fcf-inventory-consumption-<runId>-1` artifact with `overwrite:false`. Its single `manifest.json` uses schema1/kind`fcf-missing-inventory-consumed` and binds claim ref/commit/JSON SHA, planSHA, seed identities, exact run/attempt/source commit and authenticated claim-job ID. Fixed steps are `Verify one-shot FCF inventory claim` and `Retain one-shot FCF inventory consumption`. G1 requires the successful completed consumption job/steps and actual authenticated artifact ID/digest before coordinator clearance and any GET. G9 rechecks the same claim/artifact rather than consuming again. Final receipt binds it too. A successful completed consumption job remains authentic if the parent later fails; this narrow record proves reservation only and cannot bypass final target admission. Every actual source child must still be the currently running reserved attempt1 job; reading an old consumption record never starts or resumes it. No source API exists before this proof is available.

Second dispatch with the same plan has a different run ID and cannot match the protected claim. Attempt2 of the reserved run fails unconditionally, including rerun-all and rerun-failed-jobs. An interrupted first run cannot resume or free its claim; partial/indeterminate source evidence remains consumed and preserved. Fixed reviewed workflow code contains exactly one G1 and one dependent G9 capture step, with no process restart/retry path. Child job IDs and actual attempt1 metadata are bound to retained attempts; duplicate artifact names, duplicate child execution records or any unknown attempt count fail closed. A different newly reviewed plan is a separate root cumulative-budget decision, never an automatic reset of the remaining477 allowance.

A plan cannot know the ID/digest of its future output artifact. The sealed parent completion receipt therefore binds actual child artifact IDs, ZIP digests, content manifest SHAs, job IDs, run/attempt/main commit and child-plan SHAs obtained from authenticated GitHub metadata after upload. The independent reader also receives those expected identities from root's authenticated transport; a self-reported artifact ID or `verified:true` is insufficient. ## Three authentication phases: staging, continuation and final admission

These are distinct proof types and readers, not a permissive `allowRunning` flag on the final reader. All phases independently verify actual ZIP digest/size/members and explicit expected source/run/attempt/claim/plan/seed identities. No phase trusts caller-written verified/success fields. Readers and proofs are pure boundary objects; production callers must pass the actual ZIP and independently expected metadata to the appropriate reader, never construct proof objects themselves.

1. `readFcfMissingInventoryStagingArtifact({targetSlug,zipBytes,artifact,run,jobs,expected,plan,consumptionProof,now}) -> StagedInventoryProof` authenticates the already uploaded inventory while its own target job and parent run may still be running. Require the exact current attempt1 target job ID and already completed successful `Capture missing target inventory` and `Retain complete target inventory` steps; do not require later offline-audit steps, completed target job, final receipt or terminal parent. Full raw/hash/receipt/header closure is still required. Only this narrow proof may enter the in-job `auditFcfMissingInventoryOffline({stagingProof,policyHashes,now}) -> OfflineInventoryAudit`. It cannot enter target composition or claim final admissibility.
2. `readFcfMissingInventoryContinuation({inventoryZipBytes,auditZipBytes,inventoryMetadata,auditMetadata,run,jobs,expected,plan,consumptionProof,now}) -> SourceContinuationProof` authenticates complete G1 inventory and audit uploads after the exact G1 job and all required capture/upload/audit/upload steps completed successfully. The parent may still run and no final receipt is required. Rebuild full strict offline proof from raw bytes, bind actual G1 artifacts/job/claim/window/count, and recheck source age/window. This proof authorizes only the fixed dependent G9 child in the same reserved run/attempt1; it never authorizes a packet, release, new run or additional quota.
3. Final `readFcfMissingInventoryArtifact(...) -> FinalInventoryProof` and `readFcfMissingInventoryAuditArtifact(...) -> AuditedInventoryProof` require the terminal parent and authenticated successful immutable final receipt, plus exact successful selected-child job/all steps and matching inventory/audit/consumption/claim identities. Only these final proofs can enter `composeFcfCapturedTargetEvidence`. Terminal later-G9 failure is allowed only as explained below; missing receipt holds admission. Recheck raw/strict proof and ordinary freshness at final consumption.

Staging proof and continuation proof carry distinct closed kind tags and cannot be converted by replacing a tag or copying hashes. Every reader authenticates/rederives its own requirements; a locally fabricated object or a prior-phase proof is insufficient. Parent receipt generation consumes authenticated child metadata/bytes directly and does not call the final reader, so it has no dependency on its own future artifact. The receipt artifact's actual ID/digest is supplied later by final authenticated transport; no circular output ID is embedded in its own content.

Per child:2MiB per source body/prefix,8MiB manifest,192MiB total expanded and100MiB actual ZIP. No symlinks/nonregular/unsafe ancestors/preexisting output, path traversal, duplicate members, race-changed files, BOM/invalid JSON or unknown manifest properties. If the next worst-case body cannot fit, stop before requesting. Keep only one live body buffer; source bytes go into invocation-owned exclusive files with durable receipts. Authenticate the final receipt with `readFcfMissingInventoryFinalReceipt({zipBytes,artifact,run,jobs,expected,plan,claimProof,consumptionProof,childRecords,now}) -> FinalBatchReceipt`: require actual terminal expected run/attempt1, exact successful `missing-inventory-receipt` job and `Retain final FCF inventory receipt` step, single bounded manifest member, closed claim/consumption/child bindings and authenticated child ZIP/metadata records. Final authenticated reader interface is `readFcfMissingInventoryArtifact({targetSlug,zipBytes,artifact,run,jobs,expected,plan,claimProof,consumptionProof,finalReceipt,now}) -> FinalInventoryProof`. Existing target-evidence/packet integration needs an explicit new inventory input branch, with cross-protocol rejection tests; never disguise this artifact as a cache export or expand a reader to accept arbitrary lineage.

## Concrete root staging transport (implementation checkpoint)

The new Actions stages have only `contents: read` and `actions: read`. The
implementation creates no GitHub object, tag, ruleset, release, dispatch or
artifact metadata. Root first creates a private **draft** release with tag
`fcf-inventory-staging-v1` and uploads the reviewed local ZIP/approval JSON as
actual assets. Each dispatch supplies the actual asset ID and independently
reviewed SHA256. The CLI authenticates that draft release, paginates its assets,
checks the actual uploaded size, downloads through the fixed repository API and
rehashes the bytes. Publishing/deleting/changing a draft asset cannot change
accepted bytes; a missing or different asset holds the run. No public arbitrary
URL or legacy cache artifact is an input.

1. On the final reviewed main, root runs the source-free local command
   `node scripts/fcf-missing-inventory-actions.mjs pack-seed --originals-dir ABSOLUTE_ORIGINALS --source-commit REVIEWED_MAIN --output FRESH_ABSOLUTE_ZIP`.
   The command preserves the full original receipt manifest and the three exact
   marker bodies, validates all pinned hashes, and reports the actual ZIP,
   seed-manifest and original-manifest hashes. It never invents an Actions proof.
2. Root uploads that ZIP to the draft release, then dispatches `seed-stage` on
   that same reviewed main with the actual `asset_id`, `asset_sha256`,
   `asset_manifest_sha256`, and `original_manifest_sha256`. The successful run's
   actual `missing-inventory-seed` job uploads the immutable seed artifact.
3. Root authenticates that successful seed run/artifact and runs `prepare-approval`
   with `--seed-run-id`, `--seed-attempt`, `--seed-artifact-id`, `--seed-digest`,
   `--seed-commit`, `--seed-manifest-sha`, `--original-manifest-sha`,
   `--source-commit`, `--ruleset-id`, and fresh `--output`. It reads real GitHub
   metadata/ZIP, constructs the exact477 plan and reports its hash. Root reviews
   and uploads the approval JSON as a distinct draft asset. No approval asset or
   protected ruleset is assumed to exist before this root-owned preparation.
4. Root dispatches `missing-inventory` with only fixed preset
   `g1-then-g9-missing-v1` and that actual approval asset ID/SHA. Its consumption
   job waits source-free for the one protected claim. The claim template command
   `claim-template --approval ABSOLUTE_APPROVAL --run-id ACTUAL_HELD_RUN --output FRESH_ABSOLUTE_JSON`
   authenticates the held main attempt1 and emits exact claim bytes/hash.
5. Root verifies the active tag ruleset (tag target, exact reserved namespace,
   update/deletion blocked, no bypass), creates the claim blob/tree/commit with
   the reviewed main as its single parent, then performs one atomic GitHub
   `POST git/refs` for `refs/tags/fcf-inventory-claim/<planSHA>`. An existing ref
   is a consumed/lost reservation; never update/delete it or dispatch a second
   execution/attempt2 for that plan, including after zero/unknown requests.
   Root records the actual commit/JSON hashes. The workflow token cannot perform
   this mutation and checks the actual protected ref/commit/tree/blob/ruleset
   before consumption and again after source coordination.
6. The immutable consumption upload outputs supply the actual artifact ID,
   digest and manifest SHA to both source jobs. G1 captures, uploads, then audits
   its actual uploaded ZIP offline. Only the completed successful G1 job and
   independently reproduced full audit can enable G9. The receipt job always
   records authenticated known counts; missing/unknown records yield a distinct
   indeterminate diagnostic with null total and no admission.

The staging/continuation/final proof readers remain distinct. Inventory seal is
`statisticsAudit: not-run`; final target composition is still held until the
separately reviewed Task5 adapter consumes terminal reader-issued inventory,
offline audit, final receipt and consumption evidence. No actual staging asset,
claim, run or source response is asserted by these implementation tests.
